# Legacy Java Monolith → Reactive Vert.x

Research and reproducibility repository for:

**Performance and Cost Optimization in Enterprise Systems: A Quantitative Analysis of Migrating Legacy Java Monoliths to Reactive Vert.x Architectures**

## Repository

~~~text
├── paper/                 # IEEE manuscript and submission assets
├── research/              # methodology and mathematical model
├── implementation/
│   ├── legacy-monolith/   # blocking Spring/Tomcat + JDBC
│   └── reactive-vertx/    # event-driven Vert.x + reactive PostgreSQL
├── database/              # deterministic PostgreSQL fixture
├── benchmark/             # k6 workload + run/analyze helpers
├── benchmark-results/     # manuscript values and future raw runs
├── diagrams/              # architecture diagrams
└── docs/                  # reproducibility protocol
~~~

## Experimental architecture

~~~text
                         ┌───────────────┐
                         │   k6 loader   │
                         └───────┬───────┘
                                 │
                 ┌───────────────┴───────────────┐
                 │                               │
          ┌──────▼──────┐                 ┌──────▼──────┐
          │ Spring/Tomcat│                 │   Vert.x    │
          │   :8080      │                 │   :8081     │
          └──────┬──────┘                 └──────┬──────┘
                 │ JDBC/HikariCP                  │ Reactive PG
                 │                                │
                 └──────────────┬─────────────────┘
                                ▼
                         ┌─────────────┐
                         │ PostgreSQL  │
                         │   :5432     │
                         │  pg_sleep   │
                         └─────────────┘
~~~

Both services execute the same fixture query and requested delay. The experimental difference is blocking JDBC execution versus asynchronous Vert.x PostgreSQL I/O. Spring Boot documents HikariCP as its preferred JDBC connection pool when available; Vert.x documents its PostgreSQL client as reactive and non-blocking. citeturn0search5turn0search0

## Run the reproducible stack

Prerequisites: Docker, Java 21+, Maven 3.9+, and k6 for local benchmarking.

~~~bash
docker compose up --build
~~~

Smoke test:

~~~bash
curl http://localhost:8080/health
curl http://localhost:8081/health
curl 'http://localhost:8080/work?delayMs=50&itemId=1'
curl 'http://localhost:8081/work?delayMs=50&itemId=1'
~~~

Expected work responses are `legacy-ok` and `reactive-ok` respectively.

## Benchmark

Run the same workload against each target separately:

~~~bash
BASE_URL=http://localhost:8080 DELAY_MS=50 \
  SUMMARY=benchmark-results/legacy-k6-summary.json \
  bash benchmark/run-local.sh

BASE_URL=http://localhost:8081 DELAY_MS=50 \
  SUMMARY=benchmark-results/reactive-k6-summary.json \
  bash benchmark/run-local.sh
~~~

Analyze a summary:

~~~bash
python3 benchmark/analyze_summary.py benchmark-results/reactive-k6-summary.json
~~~

The default k6 scenario ramps from 50 to 5,000 virtual users. See `benchmark/README.md` for the protocol and publication-discipline requirements.

## Benchmark integrity

The values in `benchmark-results/paper-reported-results.md` are **reported by the manuscript**, not newly generated by this repository. They remain a reference baseline. New IEEE evidence must come from documented runs with raw measurements, environment metadata, workload configuration, and the exact git commit.

CI smoke tests validate build/startup and response equivalence; they are not publication-grade performance measurements.

## Research scope

The paper studies blocking versus event-driven execution, Little's Law, the Vert.x Multi-Reactor model, throughput, latency, context switching, memory footprint, cloud OpEx, and future AI-assisted refactoring.
