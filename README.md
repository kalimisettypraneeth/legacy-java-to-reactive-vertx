# Legacy Java Monolith → Reactive Vert.x

Research and reproducibility repository for **Migrating Java Services to Eclipse Vert.x: Measuring the Trade-offs**.

The [active IEEE Software manuscript](paper/ieee/manuscript.md) is a practitioner-method working draft, not a completed empirical study. Read the [submission status](paper/ieee/submission-checklist.md) and [claim audit](paper/ieee/claim-audit.md). No raw benchmark runs currently substantiate the earlier manuscript’s headline figures. Publication is not yet ready and no submission has been made.

## Experimental architecture

~~~text
                         ┌───────────────┐
                         │   k6 loader   │
                         └───────┬───────┘
                                 │
                 ┌───────────────┴───────────────┐
                 │                               │
          ┌──────▼──────┐                 ┌──────▼──────┐
          │ Spring/Tomcat│                 │   Vert.x    │
          │   :8080      │                 │   :8081     │
          └──────┬──────┘                 └──────┬──────┘
                 │ JDBC/HikariCP                  │ Reactive PG
                 │                                │
                 └──────────────┬─────────────────┘
                                ▼
                         ┌─────────────┐
                         │ PostgreSQL  │
                         │   :5432     │
                         │  pg_sleep   │
                         └─────────────┘
~~~

Both services execute the same fixture query and requested delay. The experimental difference is blocking JDBC execution versus asynchronous Vert.x PostgreSQL I/O. Spring Boot documents HikariCP as its preferred JDBC connection pool when available; Vert.x documents its PostgreSQL client as reactive and non-blocking. ([Spring JDBC configuration](https://docs.spring.io/spring-boot/reference/data/sql.html); [Vert.x PostgreSQL client](https://vertx.io/docs/vertx-pg-client/java/)).

## Run the reproducible stack

Prerequisites: Docker, Java 21+, Maven 3.9+, and k6 for local benchmarking.

~~~bash
docker compose up --build
~~~

Smoke test:

~~~bash
curl http://localhost:8080/health
curl http://localhost:8081/health
curl 'http://localhost:8080/work?delayMs=50&itemId=1'
curl 'http://localhost:8081/work?delayMs=50&itemId=1'
~~~

Expected work responses are `legacy-ok` and `reactive-ok` respectively.

## Benchmark

Run the same workload against each target separately:

~~~bash
BASE_URL=http://localhost:8080 DELAY_MS=50 \
  SUMMARY=benchmark-results/legacy-k6-summary.json \
  bash benchmark/run-local.sh

BASE_URL=http://localhost:8081 DELAY_MS=50 \
  SUMMARY=benchmark-results/reactive-k6-summary.json \
  bash benchmark/run-local.sh
~~~

Analyze a summary:

~~~bash
python3 benchmark/analyze_summary.py benchmark-results/reactive-k6-summary.json
~~~

The default k6 scenario ramps from 50 to 5,000 virtual users. See `benchmark/README.md` for the protocol and publication-discipline requirements.

## Benchmark integrity

The values in `benchmark-results/paper-reported-results.md` are **reported by the manuscript**, not newly generated by this repository. They are an unverified historical record, not a validated baseline. New IEEE evidence must come from documented runs with raw measurements, environment metadata, workload configuration, and the exact git commit.

The CI workflow checks build/startup and valid-input responses with both ordinary Docker volume storage and optional PostgreSQL tmpfs storage. These checks are not publication-grade performance measurements.

## Research scope

The revised draft explains blocking and asynchronous I/O, queueing, workload equivalence, repeatable measurement, and cost at an equivalent service-level objective. It makes no measured speedup or cost-saving claim. AI-assisted refactoring is outside the present evaluation.

## PostgreSQL with memory-backed storage

For a Linux Docker environment, use the optional override:

```bash
docker compose -f docker-compose.yml -f docker-compose.memory.yml up --build
```

This runs PostgreSQL 16 with its data directory on tmpfs. Data disappears when the container stops. It retains the same SQL, JDBC driver, reactive PostgreSQL client and password authentication. This mode changes storage behavior and must be reported as a separate benchmark configuration. See [database choice and CI diagnosis](docs/database-benchmarking.md).
